# Decisions

1. **Styling:** plain CSS with design tokens (`src/styles/tokens.css` + `global.css`) instead of Tailwind or CSS Modules. The prototype is a CSS-variable design; keeping one token sheet guarantees day/night and accent recolouring work at runtime, and avoids a build-time utility layer. Every colour comes from a token — no inline colour styles.
2. **Module registry over bespoke pages:** `src/features/modules/registry/*.ts` declares every module of the nexhrms inventory (fields, statuses, search keys, icons, ID prefix, group, path, aliases); `src/features/modules/config.ts` is only a barrel re-export. `ModulePage` renders table/form/drawers from that config so behaviour cannot drift between the 91 modules. Per-module extras live in `src/features/modules/extras.tsx`.
3. **Mock database:** one `localStorage` document (`hrms-mock-db-v1`) holding every module array, wrapped by `src/services/db.ts`. Mutations persist, `resetDemoData()` restores the seeds. Services add 200–400 ms latency so skeletons/spinners are real.
4. **Service swap:** `src/services/crud.ts` is the only place that touches the mock DB; `src/services/index.ts` exposes one typed service per module. Setting `VITE_USE_MOCKS=false` and `VITE_API_BASE_URL` plus replacing each service body with `http.*` calls (already stubbed in `src/lib/http.ts`) is the whole migration.
5. **Entity typing:** entities are exported as `type` aliases (not `interface`) so seeded literals are structurally assignable to the generic `HrRecord` row type used by the table. No `any` anywhere; `@typescript-eslint/no-explicit-any` is an error.
6. **Sorting/pagination:** TanStack Table runs in manual mode for sorting; the mock service performs search, status filter, sort and pagination, mirroring a real list endpoint (`ListParams` → `Page<T>`).
7. **Permission model:** the RBAC matrix covers all 91 modules plus the six page keys (`roles`, `plans`, `settings`, `mediaLibrary`, `calendar`, `admin`) in a persisted Zustand store (`hrms-rbac-v2`; v1 payloads migrate to the new defaults). `usePermissions()` is the only read API; `<Can>` and route guards use it. Sidebar links, toolbar buttons, drawer actions and the dashboard all derive from it.
8. **Dashboard layout:** persisted in `hrms-layout-v1` (`{ id, span, hidden }` order). dnd-kit handles reorder; ◀ ▶ and ⇅ buttons provide a keyboard/mouse alternative. Chart.js defaults (tooltip, ticks, gradient fill) are themed from tokens and re-render when the mode changes.
9. **Employee demo identity:** the demo has no auth; `DEMO_USER = 'Ava Patel'` in `src/lib/demo.ts` is used for self check-in, asset assignment and comment authorship. Role switching is a demo-only header control.
10. **Employee dashboard reduction:** rather than duplicating a second dashboard, widgets flagged sensitive (`mix`, `attr`) are filtered out for the Employee role. Same layout, fewer widgets.
11. **i18n:** every user-facing label that is shared across features lives in `src/lib/strings.ts`; module-specific labels live in the module config (a single object per language would be a drop-in replacement later).
12. **Testing:** Vitest + Testing Library cover the full-inventory RBAC defaults, registry↔seed coverage (every module has a config and seed rows, unique paths, navigation coverage), the DataTable (render, pagination, empty, delete) and the formatting helpers. Playwright is not wired up — there is no browser suite in this delivery.
13. **Full inventory, not a sample:** the brief asks for every nexhrms module. Inventory came from the sidebar (`resources/js/components/app-sidebar.tsx`) and `routes/web.php`; each model became a registry entry with its real status set, and the seed files mirror the Laravel factories. Modules are grouped exactly like nexhrms (People, Organization, Lifecycle, Attendance & Leave, Payroll, Recruitment, Performance, Training, Workplace, Documents, Business & Billing, Platform Admin).
14. **Bespoke pages stay bespoke:** Roles, Plans, Settings, Media, Calendar and the Super Admin overview do not fit a CRUD table (matrices, charts, tabs, grids), so they are real React pages under `src/features/{roles,plans,settings,media,calendar,admin}` and share the same shell, guards and design tokens.
15. **Settings persistence:** settings are a schema-driven page (`SECTIONS` array) with one Zustand store (`hrms-settings-v1`) rather than 11 separate forms, so adding a field is one line and the draft/save/reset flow is identical in every tab. Company, branding, localization, email, payments, storage, notifications, security, SEO, landing page and system sections mirror the nexhrms settings screens, including custom landing pages, cache and webhooks.
16. **Platform vs company audiences:** navigation groups carry an `audience` (`platform`/`company`) and the RBAC matrix hides platform-only keys (`companies`, `admin`, plan orders/coupons, permissions) from every company role. Super Admin therefore sees the platform admin group; other roles see Business & Billing instead.
